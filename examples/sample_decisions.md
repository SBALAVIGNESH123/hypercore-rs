# Architecture Decision Records

## ADR-001: Local-First Architecture

**Date**: 2025-06-15  
**Status**: Accepted

We decided to build Hypercore as a fully local system rather than a cloud service. The reasoning:

1. Privacy — users' documents never leave their machine
2. Latency — no network round-trips for inference
3. Ownership — users control their own AI, models, and data
4. Cost — no recurring API fees

We chose Rust over Python for the core runtime because we wanted a single static binary with predictable memory usage. Python's GIL and garbage collector make memory budgeting unreliable for inference workloads.

## ADR-002: SQLite Over Postgres

**Date**: 2025-07-20  
**Status**: Accepted

Selected SQLite instead of Postgres for the knowledge store.

Rationale: Hypercore is a single-user local tool. Postgres requires a separate server process, configuration, and maintenance. SQLite gives us ACID transactions, FTS5 full-text search, and zero deployment complexity.

Tradeoff: We lose concurrent write throughput and network-accessible queries. We accepted this because the use case is single-user local inference, not a multi-tenant service.

## ADR-003: Keyword Extraction Over LLM Extraction

**Date**: 2025-08-01  
**Status**: Accepted, under review

Opted for keyword heuristic extraction ("decided to", "prefer", etc.) instead of running every chunk through the LLM during ingestion.

Rationale: Users hate waiting. Ingestion should be fast. LLM extraction would add 10-30 seconds per chunk on CPU hardware. Keyword matching processes 150 chunks in under a second.

Tradeoff: We miss implicit decisions. "After comparing X and Y we went with Y because..." gets caught, but "For now we'll keep everything local" does not. We plan to add LLM-powered extraction as an optional background pass in v2.

## ADR-004: Feedback-Driven Development

**Date**: 2025-08-15  
**Status**: Accepted

Every insight generated by the memory system asks the user to rate it:

1. Obvious
2. Somewhat useful  
3. Surprising
4. Changed how I think

This data is persisted and will drive product decisions. If nobody ever picks 3 or 4, the insight engine needs fundamental changes. If several users consistently pick 4, we've found product-market fit.

We prefer measuring user reactions over measuring technical metrics like retrieval accuracy. A system with 90% retrieval accuracy that produces only obvious insights is worse than one with 50% accuracy that occasionally generates genuine surprises.
